## Background

As a **UX Engineer**, we are embedded directly within the **design team** structure to collaborate closely with designers every day. This proximity previously succeeded in birthing the mature and widely adopted [BLUE Web Design System](/projects/blue-web-design-system) across all tribes, even achieving a score of <strong className="text-primary font-semibold">8.48</strong> in reducing redundancy and <strong className="text-primary font-semibold">8.42</strong> in accelerating delivery based on the mid-2024 statisfaction survey.

However, the condition of the mobile design system is vastly different because its development was handled by developers outside the design team structure, who were more focused on feature development. As a result, <strong className="text-primary font-semibold">the mobile design system lagged behind the web</strong> and was still using the old standard (**BLUE 2.0**), with inconsistent design languages between the Customer and Seller ecosystems. In fact, over 85% of Blibli users access the application via mobile devices.

Based on these conditions, we initiated the development of the <strong className="text-primary font-semibold">BLUE Android Design System</strong> to align the visual and technical standards across the entire Blibli application ecosystem through collaboration between UX Engineers, designers, and Android developers.

## Problem Identification

Based on the background above, there were several main problems in the development of the mobile design system, namely:

* <strong className="text-primary font-semibold">The mobile design system lagged behind the web</strong> because it lacked focused management.
* **The use of the old design standard (BLUE 2.0)** caused inconsistencies in the design language across platforms and services.
* Fragmented maintenance processes led to redundancy and hindered team work efficiency.
* The absence of a single standard on the mobile platform caused inconsistent user experience quality.

## Goals and Objectives

The main goal of this project is to build the <strong className="text-primary font-semibold">BLUE Android Design System</strong> as a single standard that aligns the design language and technical implementation across the entire Blibli application ecosystem.

To achieve this goal, several key objectives were established as follows:

* <strong className="text-primary font-semibold">Equalize the quality of the mobile design system with the web</strong> by strengthening cross-role collaboration (UX Engineer, designer, and Android developer).
* Unify the Customer and Seller ecosystems into the **BLUE 3.0** standard to replace the old standard (**BLUE 2.0**).
* Build a centralized design system as a Single Source of Truth (SSOT) to reduce redundancy and fragmentation in the maintenance process.
* Align the design language across platforms to ensure a consistent user experience throughout the Blibli application ecosystem.

## Roles and Responsibilities

In this project, I acted as part of the **UX Engineer** team, collaborating directly with designers and Android developers, with responsibilities including:

* Developing reusable, scalable, and consistently implemented BLUE Android components.
* Establishing the foundation of design tokens such as color, typography, sizing, opacity, and elevation to maintain visual consistency.
* Developing an icon library to reduce asset redundancy and maintain visual consistency.
* Ensuring the quality and consistency of the design system through technical documentation, code reviews, testing, and periodic evaluations.
* Supporting cross-platform design system synchronization to ensure a consistent user experience across the Blibli application ecosystem.

### 3. Development and Implementation

The development and implementation of the BLUE Android Design System were carried out iteratively through several sprints with a collaborative and continuous approach. All processes ran in parallel and continued to evolve according to needs in each sprint.

* The initial phase focused on migrating the design token script and component library to a new repository as the main foundation of the design system.
* An audit was conducted on the migrated code and components to map their conformity with BLUE design system standards and identify areas that needed fixing or refinement.
* Making improvements based on audit results through adjustments to token values and refining components both visually and in code.
* Developing new components iteratively to complete the library needs, alongside the bug fixing process and standard adjustments.
* The team also initiated an icon library as a new icon system on the Android platform to fulfill visual asset needs that were previously unavailable.
* All development results must go through a cross-team code review process and Design QA before being implemented into production.
* The team also built a CI/CD pipeline with the RnD team to automate the build process and distribution of the Android Design System library.
* The library release process is carried out by the UX Engineer team through the CI/CD pipeline with artifact distribution to Google Artifact Registry (GAR), accompanied by release notes and release announcements to facilitate adoption by the developer team.
* Implementation was carried out through pilot projects on several selected projects to validate the use of the design system in a real environment.
* Each sprint concluded with a retrospective session to evaluate the workflow and improve the effectiveness of team collaboration.


## Results
After approximately six months of development, the first version of the BLUE Android Design System was successfully released in July 2024. This release presented three main foundations consisting of the Component Library, Design Tokens, and Icon Library to support the standardization of Android development in a more consistent, modular, and centralized manner for all products within the Blibli application ecosystem.

### Design Tokens
Design Tokens act as a single source of truth for basic visual elements such as color, typography, sizing, spacing, and elevation. The token structure in BLUE Android adopts a tiered structure consisting of:

* **Global Tokens** which serve to store base values (raw values) like primary colors and constant sizing numbers.
* **Alias Tokens** which assign specific meanings or functions to global values, acting as the primary bridge for theming needs such as light mode and dark mode automatically.
* **Component Tokens** which bind specific values directly to component library elements so that global changes do not break the structure of other components.

### Icon Library
The Icon Library is a dedicated library that acts as the center for modular management of all icon assets on the Android platform. Through this initiation, the entire iconography system is distributed through a single gateway in the form of optimized Vector Drawables integrated directly into the Jetpack Compose code.

This system makes it easier for developers to use icons consistently, eliminates the manual import process of individual XML asset files that are prone to duplication, and significantly helps reduce the final size of the application installation file (APK size optimization).

## Impact

The implementation and management of the BLUE Android Design System have a positive impact on product development efficiency as well as professional competency development.

### Impact on the Company

* Visual and product interaction consistency improved through the standardization of the BLUE Android Design System.
* Android feature delivery processes became faster by utilizing ready-to-use components from the centralized library.
* Reduced asset duplication through the implementation of a centralized icon library, eliminating the need for additional scripts to detect asset duplication previously used by Android developers.
* Supported the Blibli rebranding process on the Android platform through the implementation of a more consistent and standardized design system.
* Cross-team collaboration between UX Engineers, Android CEs, Android SEs, and Product Designers became more directed through standardized workflows.
* Independent repository management under the UX Engineer team helped reduce cross-team dependencies and facilitated the maintenance of UI assets in the long term.
* The library distribution process became more efficient through the implementation of CI/CD workflows and a standardized release pipeline.

### Personal Impact

* Enhanced technical understanding of implementing design tokens and component libraries based on Jetpack Compose on the Android platform.
* Honed skills in building and managing large-scale design systems from initiation to code quality standardization.
* Strengthened experience in technical governance through cross-team code review processes and Design QA coordination.
* Sharpened analytical skills in conducting code audits and systematically refining components.
* Provided new experience in managing library release processes, CI/CD pipelines, and distributing artifacts to the Google Artifact Registry (GAR).
